drtk.source_features
====================

.. currentmodule:: drtk

.. autosummary::
    :nosignatures:

    source_feature_stencil
    sample_feature_stencil
    source_feature_stencil_ref
    sample_feature_stencil_ref

Sample source-image features onto a deformed surface while respecting
occlusion, cuts, and local surface ownership. Gradients propagate to the
source features, receiving surface, and occluding geometry.

See :doc:`../tutorials/DRTK_Tutorial_source_features` for a rendered example,
an optimization visualization, and the complete runnable script.

Two reusable operations
-----------------------

``source_feature_stencil`` computes four texel indices and four weights per
surface query. ``sample_feature_stencil`` applies them to arbitrary-channel
feature maps. Reuse the same stencil across feature banks on the same grid,
within the same geometry evaluation. Rebuild it after changing geometry,
topology, opacity, or the source camera.

Queries are attached to a face by **3D barycentric coordinates**. A floating
point depth comparison cannot disambiguate two overlapping surfaces. Each tap
instead follows the query's local surface through indexed manifold neighbors.
Open boundaries, cuts, projected folds, and nonmanifold ambiguity stop that
continuation. Global connected-component identity is insufficient: one
connected mesh can occlude itself.

For receiver face :math:`r`, source visibility is the transmittance of the
faces preceding it in the transparent renderer's stable mean-depth/face-index
order:

.. math::

   T_r(p)=\prod_{f\prec r}\left(1-\alpha_f(p)\right).

The receiver's own opacity is excluded. Opacity is known geometric/material
opacity, including feathering. It must be independent of an appearance
network that consumes the sampled features; otherwise visibility would depend
on its own output. There is no per-pixel depth sorting or differentiation
through sort changes.

With bilinear coefficients :math:`b_{qj}` and source features :math:`F_j`,

.. math::

   w_{qj}=b_{qj}T_{qj},\qquad
   S_q=\sum_{j=1}^{4}w_{qj}F_j,\qquad
   c_q=\sum_{j=1}^{4}w_{qj}.

The output is the **unnormalized feature sum and confidence**. There is no
division by a small alpha/confidence. Feed both to the refinement model and
preserve anchor features separately. Do not multiply :math:`S_q` by
:math:`c_q` a second time.

An in-image tap keeps its index even when its weight is zero. This lets
backward evaluate the feature value that would be revealed by a moving
occlusion boundary. A zero-weight tap contributes nothing in forward.

Gradients
---------

Source-visibility boundary gradients are enabled by default
(``edge_gradients=True``). Do not wrap the result in :func:`edge_grad_estimator` again. Target-view transparent rendering
has its own separate boundary gradient.

The boundary signal measures the change in source features and confidence.
For upstream gradients :math:`g_S,g_c`,

.. math::

   \frac{\partial L}{\partial w_{qj}}
   =\langle g_{S_q},F_j\rangle+g_{c_q}.

This scalar adjoint multiplies the one-sided visibility change and is
accumulated onto the boundary vertices. A heavy downstream MLP or transformer
can therefore send a loss signal to the occluding geometry through normal
``loss.backward()``. This is DRTK's local boundary-gradient estimator, not an
exact derivative of the discrete hard rasterizer.

Smooth derivatives of projection, bilinear weights, and material opacity are
computed separately. Ordinary shared tessellation edges do not introduce
artificial gradients. A zero-opacity occluder has zero visibility jump;
an edge completely hidden behind an opaque occluder also has zero jump.
Receiver-domain boundaries are a distinct source of feature-admission changes.
Exact opaque values are supported.

.. list-table::
   :header-rows: 1
   :widths: 42 58

   * - Quantity
     - Gradient
   * - Vertices, query barycentrics, source features, material opacity
     - Smooth derivatives within a fixed visibility configuration.
   * - Visibility/receiver-domain boundaries
     - Integrated edge-gradient estimate to geometry.
   * - Face IDs, connectivity, sort order, discrete local-walk branches
     - No ordinary derivative; use sampled-topology loss estimation for topology logits.
   * - Second derivatives
     - Unsupported.

The reference functions support CPU tensors and smooth gradients only;
they do not provide visibility-boundary gradients.

Coordinates and supported inputs
--------------------------------

``v_pix`` uses source pixel XY and camera Z. Integer XY is a pixel center;
there is no Y flip. For a query with 3D barycentrics :math:`\beta`,

.. math::

   z_q=\sum_i\beta_i z_i,\qquad
   p_q=\frac{\sum_i\beta_i z_i p_i}{z_q}.

Use the existing camera projection utilities before calling the stencil.
When sampling a smaller feature map, scale the source intrinsics or projected
coordinates with the half-pixel convention:
``x_f = (x + 0.5) * W_f / W - 0.5``. Banks with different grids require
different stencils. ``return_queries=True`` returns normalized UV compatible
with ``grid_sample(..., align_corners=False)`` and camera Z.

These operations require CUDA tensors. The stencil uses float32 geometry and
weights. Sampling accepts float16, bfloat16, and float32 feature images,
arbitrary channel counts, and strided inputs. Results are accumulated in
float32. Backward is not guaranteed to be bitwise deterministic.

``source_feature_stencil`` does not support CUDA graph capture. Reuse a stencil
across same-grid feature banks, and rebuild it when geometry, topology,
material opacity, or the source camera changes.
